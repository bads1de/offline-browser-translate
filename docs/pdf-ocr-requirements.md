# スキャン PDF の OCR 要件定義書

- 対象: 本リポジトリ (Local LLM Translator / offline-browser-translate v2.2.3) の PDF ビューア
- 作成日: 2026-11-27（2026-11-27 改訂: Tesseract.js 案を破棄し、ローカルサーバーの VLM 方式に一本化）
- ステータス: **要件定義のみ (未実装)** — 実装は Phase 1 から
- 配布形態: **個人利用** (ローカルで `chrome://extensions` に読み込む)。ストア公開は考慮しない
- 関連: `docs/pdf-translation-requirements.md`（PDF 翻訳本体。本書はその Phase 3「OCR」を独立させたもの）
- 決定済みの方針:
  1. 起動は**自動フォールバック**（テキストが取れないページだけ OCR）
  2. OCR は**既存のローカルサーバー上で動く VLM** に投げる。**別サーバーは立てない**
  3. **Tesseract.js は採用しない**（同梱 wasm・言語データを持たない）
  4. 「テキスト層付き PDF」の書き出しは**今回のスコープ外**（Phase 4）
  5. 基準モデルは **PaddleOCR-VL 1.6**（0.96B / Apache-2.0）

---

## 1. 目的・背景

現在の PDF 翻訳は pdf.js の `page.getTextContent()` で取り出したテキストだけを翻訳する。テキスト層を持たない PDF（紙のスキャン、スキャンアプリ出力、FAX、画像を貼っただけの PDF）では抽出結果が 0 件になり、ビューアは

```
テキストが見つかりません。スキャン PDF には対応していません (OCR は Phase 3 以降)。
```

と表示して停止する（`pdf/viewer.js` の `afterLoad()`）。この穴を埋めるのが本要件の目的。

**設計の要点は2つ。**

1. **新しい翻訳経路を作らない。** `LctPdfParagraphs.extractParagraphs()` は `{ str, transform, width, height }` を持つ item 配列を受け取る純粋関数なので、OCR の行ボックスを同じ形に変換して渡せば、段落復元・翻訳・キャッシュ・用語集・オーバーレイ・訳 PDF 書き出しが**すべて無変更で動く**。位置情報が取れないモデルでも、テキストを段落として流せば対訳表示は成立する
2. **OCR エンジンを同梱しない。** 本拡張はもともと「ローカル LLM サーバーを自分で立てられる人」向けのツールである。その人が OCR のためだけに別のランタイム（Tesseract の wasm と言語データ 12MB）を抱える理由は薄い。llama.cpp / Ollama / LM Studio はいずれも複数モデルを1エンドポイントで扱えるため、**OCR モデルを1つ追加するだけ**で済む

### 1.1 なぜ Tesseract.js を落としたか

| 観点 | Tesseract.js 同梱 | ローカルサーバー VLM（採用） |
| --- | --- | --- |
| ユーザーの準備 | 不要 | OCR モデルを1つダウンロード（既存サーバーに追加） |
| 日本語の精度（スキャン・傾き・表） | 低〜中（2016年式モデル） | 高（PaddleOCR-VL 級） |
| 拡張のサイズ | +10〜12MB | ±0 |
| manifest / CSP 変更 | `'wasm-unsafe-eval'` 追加、worker 設定が必要 | **変更なし** |
| オフライン | 完全（LLM サーバー不要） | LLM サーバー必須（既存の前提と同じ） |
| 表・数式 | 崩れる | Markdown / 構造付きで返る |
| 失敗時の性質 | 文字を落とす | 存在しない文字を生成することがある |

オフラインで OCR したい人だけが損をするが、本拡張は元々ローカルサーバーが必須であり、PDF 翻訳もサーバーが止まれば動かない。**OCR だけ別ランタイムを持つ非対称性を解消する**ほうが筋が通る。

### 1.2 基準モデル: PaddleOCR-VL 1.6

**`PaddleOCR-VL 1.6`（0.96B, Apache-2.0）を基準モデルとする。**

| 項目 | 内容 |
| --- | --- |
| 配布 | `PaddlePaddle/PaddleOCR-VL-1.6-GGUF`（本体 `PaddleOCR-VL-1.6-GGUF.gguf` 936MB ＋ `PaddleOCR-VL-1.6-GGUF-mmproj.gguf` 882MB ＝ 約1.82GB） |
| 言語 | 日本語を含む109言語 |
| 強み | 表・数式・チャート・印鑑。OmniDocBench v1.6 で 96.34（0.9B 級の上位） |
| プロンプト | `OCR:` で読み順のプレーンテキスト、`Spotting:` で行単位の位置付き出力 |
| 実行 | llama.cpp / LM Studio / Ollama / llama.app から同一ウェイトで動く（HF のモデルカードに各手順あり） |

**採用理由**: 0.9B 級で「日本語」と「行単位の位置」を同時に満たす唯一の候補で、公式 GGUF があるため変換作業が不要。位置が取れれば既存のオーバーレイにそのまま流せ、取れなくても `paddle-ocr` に降格すれば対訳表示は成立する。

**既知の注意**: モデルカードに「llama.cpp では性能が落ちる場合がある」と明記されている。`Spotting:` の位置は特殊トークンとして出力されるため、サーバー側がトークンを落とすと位置が取れない（その場合は位置なしとして扱い、対訳表示に降格する）。

## 2. スコープ

### 2.1 含む

- テキスト層を持たないページの検出と、そのページだけの自動 OCR
- ページ画像を既存プロバイダ（OpenAI 互換 / Ollama）へ送る vision リクエスト
- モデル別のプロンプトプロファイル（PaddleOCR-VL / dots.ocr / GLM-OCR / 汎用）
- 出力のパース（プレーンテキスト / JSON / 位置付き出力）
- 位置情報がある場合の bbox item 変換、無い場合の対訳専用フォールバック
- 既存の段落復元・翻訳パイプラインへの合流
- ページ単位の進捗表示・中断・失敗時の縮退
- OCR 結果のローカルキャッシュ（同じ PDF を開き直したときに再 OCR しない）
- OCR の有効/無効、OCR モデル名、プロンプトプロファイル、画像解像度の設定

### 2.2 含まない

- **OCR エンジンの同梱**（Tesseract.js / ONNX Runtime / PP-OCR の wasm 版は採用しない）
- **テキスト層付き（検索可能）PDF の書き出し** — Phase 4。現行の訳 PDF 書き出しは画像ベースのまま
- レイアウト保持の再組版（原文の文字を消して訳文を流し込む）— 恒久的にスコープ外
- 手書き文字の認識保証（モデル依存。誤認識は許容し、対訳表示で目視できることを保証する）
- 数式の LaTeX 化、図表の再構成（モデルが返した Markdown/表はそのまま文字として扱う）
- クラウド OCR API への送信（方針として禁止）
- ページ画像の永続保存（リクエスト時に canvas から生成して捨てる）

## 3. ユーザー像・利用シーン

- 既に llama.cpp / Ollama / LM Studio で翻訳用モデルを動かしている
- 行政の公開資料・古い論文・紙の契約書を PDF で受け取り、日本語（または英語）で読みたい
- スキャン PDF の中身をコピーしようとして、できないことに気づいた
- 数十ページの資料を、読みながら順次処理したい
- GPU があるとは限らない（CPU でも 0.9B クラスの OCR モデルなら実用範囲）

## 4. 機能要件

### FR-1 OCR 対象ページの判定（自動フォールバック）

- `buildPages()` でページごとに `getTextContent()` の結果を段落復元にかけ、次のいずれかを満たすページを「OCR 対象」とする
  - 段落が 0 件
  - 抽出テキストの実質文字数（空白・記号を除く）が 20 文字未満
- 白紙ページを避けるため、`page.getOperatorList()` を走査し、画像 XObject（`paintImageXObject` / `paintInlineImageXObject`）が 1 つも無いページは対象外とする
- 判定結果はページ要素に `data-ocr="pending|running|done|failed|skipped"` として持たせ、UI から参照できる
- 判定は**ページ単位**。テキストページとスキャンページが混在する PDF で、テキストページの翻訳結果を一切変えない

### FR-2 OCR リクエスト

- 送信先: 既存の設定解決をそのまま使う（`provider` / `ollamaUrl` / `lmstudioUrl`）。**OCR 用に別 URL は持たない**（設定 `pdfOcrModel` でモデル名だけ差し替える）
- モデルの選び方:
  - **llama.cpp router mode**（`llama-server --models-dir ... --models-max 2`）なら、同じ `:8080` に翻訳モデルと OCR モデルが同居し、`model` フィールドだけで振り分く
  - **Ollama** は単一エンドポイントで `model` を切り替える。両方を常駐させるには `keep_alive` を長めにする
  - **LM Studio** は `:1234` のまま `model` を差し替える（同時ロード数はアプリ側の設定に従う）
- 画像の生成:
  - pdf.js のページを OCR 専用の別 canvas に描画する（表示用 canvas とは分離。ズームや dpr に依存させない）
  - 長辺 `pdfOcrMaxEdge`（既定 1600px、上限 2400px）に縮小し、JPEG quality 0.85 で base64 化
  - 1ページあたり 200〜500KB 程度を想定
- リクエスト形式（プロバイダ差の吸収）:
  - OpenAI 互換（llama.cpp / LM Studio / vLLM）: `messages[0].content = [{type:'text'}, {type:'image_url', image_url:{url:'data:image/jpeg;base64,...'}}]`
  - Ollama: `messages[0].content = 'プロンプト'` + `messages[0].images = [base64]`（data URI ではなく素の base64）
- パラメータ: `temperature: 0`（OCR に創造性は不要）、`stream: false`、`max_tokens` は既定 4096（ページ全文が収まる範囲で設定可）
- 1リクエスト = 1ページ。並列化はしない（モデル常駐とメモリを優先）
- **OCR パスを先に完了させる**: ページごとに「OCR → 翻訳」を交互に行うと、モデルが毎回入れ替わってロードし直しになる（特に `--models-max 1`）。したがって「OCR 対象ページを先に全部処理 → その後 既存の翻訳フロー」の2段階にする。ただし可視ページを最優先し、残りはバックグラウンドで進める
- 進捗は「OCR 3/12 ページ」として翻訳進捗と区別して表示する
- `AbortController` で中断可能。中断時は実行中ページを破棄し、以降を `skipped` にする
- タイムアウトは1ページ 180 秒。超過で `failed`

### FR-3 プロンプトプロファイルと出力パース

- 設定 `pdfOcrProfile` で以下を選ぶ。既定は `auto`（モデル名から推定、外れたら `generic`）

| プロファイル | 送るプロンプト | 期待する出力 | 位置情報 |
| --- | --- | --- | --- |
| `paddle-ocr`（既定） | `OCR:` | プレーンテキスト（読み順） | なし |
| `paddle-spotting` | `Spotting:` | 位置トークン付きの行テキスト | あり（行ポリゴン） |
| `dots-json` | JSON スキーマ（`bbox`, `category`, `text`） | JSON 配列 | あり（0〜1000 正規化を想定） |
| `glm-json` | スキーマ指定プロンプト | JSON | モデル次第 |
| `generic` | 「画像内の本文を読み順でプレーンテキストで出力。表は行ごとに。説明や前置きは書かない」 | プレーンテキスト | なし |

- パースは `pdf/ocr.js` の純粋関数として実装する:
  - JSON はコードフェンス・前置きを除去してから最小限の括弧マッチで抽出（既存の構造化出力リトライ機構は翻訳用なので流用しない）
  - `bbox` は `[x0,y0,x1,y1]` / `{x,y,w,h}` / 0〜1000 正規化 / ピクセル の揺れを吸収し、**必ず画像ピクセル座標に正規化**してから次段へ渡す
  - 位置トークン方式（`paddle-spotting`）は、サーバーがトークンを保持している場合のみ成立する。パースに失敗したら `generic` 相当（位置なし）に自動降格する
  - Markdown（`|` の表、`#` 見出し、`**` 強調）は素のテキスト行に正規化する。表は「1行 = 1行」として保持し、セルはタブではなく ` / ` で連結する
- 出力が空、または極端に短い（元ページのインク量に対して想定の2割未満）場合は「認識失敗」とみなし、1回だけ `generic` で再試行する

### FR-4 位置情報の有無による表示の分岐

- **位置あり**: pdf.js item に変換し、オーバーレイに訳文を重ねる（既存の `positionBox()` を使用）
- **位置なし**: 段落を積んだ対訳ビューを既定にする。ページ上部にバナーで「このページは画像のため OCR で読み取りました（対訳表示）」と出し、ワンクリックでオーバーレイ（位置なし＝訳文はページ下にまとめる）に切り替えられるようにする
- どちらの場合も、**OCR 原文は常に参照できる**（対訳モードで原文列に出す）。VLM は文字を生成することがあるため、原文との突き合わせを UI で保証する
- ページ見出しに `OCR` バッジを表示する（位置なしの場合は `OCR・位置なし`）

### FR-5 既存パイプラインへの合流

- **位置あり**: bbox を pdf.js の `transform` に変換して `extractParagraphs(items, vp)` に渡す。変換式は次のとおり（`S = 描画スケール`、`H = viewport.height`、元 bbox は左上原点）

  ```
  x_pdf  = box.x0 / S
  y_pdf  = H - (box.y1 / S)          // 行の下端を基線とみなす
  width  = (box.x1 - box.x0) / S
  fs     = (box.y1 - box.y0) / S     // 行の高さをフォントサイズとみなす
  transform = [fs, 0, 0, fs, x_pdf, y_pdf]
  ```

- **位置なし**: 正規化したテキストを行単位で分割し、`str` のみを持つ疑似 item を上から順に並べて `extractParagraphs` に渡す（`transform` の y は行番号から単調に生成する）。段落復元の行連結・2カラム判定は効かなくなるが、翻訳と対訳表示は成立する
- 以降の翻訳は既存の `TRANSLATE` メッセージ経路。キャッシュキーも既存のまま（同一テキストなら訳を再利用）
- 用語集・カスタムプロンプト・リクエスト形式など既存設定はすべて効く
- OCR 由来の段落には `data-source="ocr"` を付け、表示の注記と再実行の判定に使う

### FR-6 OCR 結果のキャッシュ

- ページ単位の OCR 結果（パース済みの行テキスト・bbox・プロファイル）を IndexedDB に保存する
- キー: `PDF のハッシュ + ページ番号 + モデル名 + プロファイル + maxEdge`
- 保存先は `pdf/pdf-store.js` の既存 DB に専用ストアを追加する（バイト列ストアとは分ける）
- ヒットした場合はリクエストを送らず、変換済み item を復元して翻訳だけ行う
- 合計 50MB を超えたら古いものから削除する

### FR-7 設定

`settings/defaults.js` に追加する（`provider` / `ollamaUrl` / `lmstudioUrl` / `selectedModel` は既存のものを再利用）。

- `pdfOcrEnabled` : 既定 `false`（既定は無効。設定画面でモデルを選んだときに有効化を促す）
- `pdfOcrModel` : 既定 `''`（空なら OCR しない。例 `PaddleOCR-VL-1.6-GGUF.gguf`）
- `pdfOcrProfile` : 既定 `'paddle-ocr'`（`paddle-ocr` / `paddle-spotting` / `auto` / `dots-json` / `glm-json` / `generic`）
- `pdfOcrMaxEdge` : 既定 `1600`（1200〜2400）
- `pdfOcrMaxTokens` : 既定 `4096`

Options 画面の PDF セクションに、モデルのドロップダウン（`/v1/models` または `/api/tags` の一覧から選ぶ）、プロファイル、解像度、有効トグルを置き、次の補足を出す。

> OCR は既存のローカルサーバーに追加した vision モデルで実行します。別のサーバーは不要です。llama.cpp の router mode を使う場合、`llama-server --models-dir <フォルダ> --models-max 2` で翻訳モデルと同居できます。`--models-max 1` だとページごとにモデルが入れ替わり非常に遅くなります。

### FR-8 失敗時の縮退・手動再実行

- OCR に失敗したページは**原文画像のまま**表示し、バナーに理由（タイムアウト / モデル未ロード / コンテキスト超過 / 出力パース失敗）と「再試行」ボタンを出す
- OCR モデルが未設定の場合は、現行の「テキストが見つかりません」バナーに**設定画面へのリンク**を足す（行き止まりにしない）
- 1ページだけ失敗しても他のページの処理は継続する
- 「このページを OCR し直す」でキャッシュを捨てて再実行できる

### FR-9 テキスト層付き PDF の書き出し（Phase 4・今回対象外）

- 訳 PDF に不可視テキスト層を載せ、検索・コピー可能にする
- 現行の `pdf/pdf-write.js` は画像のみの PDF を組み立てるため、テキスト描画（`Tr 3`）とフォント埋め込みの追加が必要。工数が大きいため独立フェーズとする

## 5. 非機能要件

### NFR-1 プライバシー

- **ページ画像はローカルホストにのみ送る。** 送信前に `baseUrl` のホストが `localhost` / `127.0.0.1` / `::1` であることを検証し、それ以外なら OCR を実行せずエラーを出す（画像はテキストより機微度が高いため、翻訳より厳しく扱う）
- 画像をディスクに保存しない（canvas から生成して送信後に破棄）
- OCR 結果のキャッシュはローカルの IndexedDB のみ
- 外部 CDN・外部モデル配布元への通信は一切行わない（そもそも同梱物が無い）

### NFR-2 性能

- 1ページあたりの目標: GPU で 2〜10 秒、CPU（0.9B クラス）で 10〜40 秒
- 可視ページを優先し、スクロールに追従して先読みする（既存の IntersectionObserver を利用）
- モデルの入れ替えコストを避けるため、**OCR パス → 翻訳パスの2段階**で実行する（FR-2）
- テキスト PDF では vision リクエストを一切送らない。画像生成も行わない
- 画像の長辺上限と `max_tokens` でコンテキスト超過を予防する

### NFR-3 信頼性

- OCR の失敗でビューア全体を止めない。失敗ページは原文画像のまま表示する
- 1ページ 180 秒でタイムアウトし、そのページを `failed` にする
- 出力が壊れている（JSON 不正・空・極端に短い）場合は 1 回だけ汎用プロンプトで再試行し、それでも駄目なら失敗扱い
- 100MB 超 / 500 ページ超の PDF では OCR を既定で無効化し警告を出す（リクエスト数とメモリの保護）
- 中断しても完了済みページのキャッシュは保持する

### NFR-4 権限

- **manifest の変更は不要**。`host_permissions` は既に `http://localhost/*` を持ち、`optional_host_permissions` に `<all_urls>` がある
- CSP の変更も不要（WASM を使わないため `'wasm-unsafe-eval'` は追加しない）
- 新規の `web_accessible_resources` も不要

### NFR-5 ライセンス

- 新規の同梱物・依存はゼロ。モデルのライセンス（PaddleOCR-VL: Apache-2.0、dots.ocr: MIT、GLM-OCR: MIT 等）はユーザーが自分の環境に入れるものであり、本拡張には含まれない
- 参考実装（OCR-buddy、local-llm-pdf-ocr 等）は**設計参照のみ**。コードは流用しない

### NFR-6 コードスタイル

- 既存どおりバニラ JS・ビルド工程なし
- 判定・変換・パース・キャッシュキーは DOM 非依存の純粋関数として `pdf/ocr.js` にまとめ、`node tests/pdf-ocr-test.mjs` で検証する

## 6. 影響範囲・設計ポイント

| ファイル | 変更概要 |
| --- | --- |
| `pdf/ocr.js` | ページ判定、canvas 描画と base64 化、vision リクエスト組み立て、出力パース、bbox→item 変換、キャッシュキー（新規） |
| `background/translate.js` | vision 用のリクエスト組み立て（`content` 配列 / Ollama の `images`）。OCR はテキスト生成と別関数にし、既存の翻訳整形を通さない |
| `background/providers.js` | モデル一覧の再利用（OCR モデル選択 UI 用）。変更は最小 |
| `pdf/viewer.js` | `buildPages()` から OCR 対象を判定してキュー化。`afterLoad()` の「テキストなし」分岐を OCR 経路へ。2段階実行の制御 |
| `pdf/viewer.html` / `viewer.css` | OCR バッジ、バナー、進捗表示、対訳専用モードのスタイル |
| `pdf/pdf-store.js` | OCR キャッシュ用ストアの追加 |
| `settings/defaults.js` | `pdfOcrEnabled` / `pdfOcrModel` / `pdfOcrProfile` / `pdfOcrMaxEdge` / `pdfOcrMaxTokens` |
| `options/options.html` / `options.js` | PDF セクションに OCR 設定と補足文 |
| `tests/pdf-ocr-test.mjs` | bbox 正規化・JSON 抽出・Markdown 正規化・キャッシュキーのユニットテスト（新規） |
| `docs/pdf-translation-requirements.md` | 2.2 と Phase 計画から本書へ参照を張る（実施済み） |
| `manifest.json` | **変更なし** |

設計で特に注意する点:

- **モデル切り替えのスラッシング**が最大の性能リスク。`--models-max 1` や Ollama の既定 `keep_alive` だと、OCR と翻訳のたびにモデルをロードし直して1ページ数十秒のオーバーヘッドになる。2段階実行（FR-2）と、設定画面での推奨構成の明示で回避する
- **vision 非対応モデルに画像を送ると 501** が返る（llama.cpp）。エラーメッセージをそのまま出さず「選択したモデルは画像入力に対応していません」と翻訳して表示する
- **コンテキスト長**: OCR は入力（画像トークン）も出力も長い。llama.cpp は `-c 8192` 以上を推奨（GLM-OCR では `-c 12000` の報告例がある）。不足時は出力が途中で切れるため、`finish_reason: 'length'` を検出して失敗扱いにする
- **位置の粗さ**: VLM の bbox は「ブロック単位」のことが多く、行単位のオーバーレイには粗い。位置ありでも行が大きく外れる場合は、その段落だけ対訳列に逃がす（`data-ocr="done"` + `data-position="coarse"`）
- **幻覚**: VLM は存在しない行を生成しうる。対訳モードで原文を見せること、ページ見出しに `OCR` バッジを出すことを必須とする
- **回転・傾き**: スキャン PDF は 90 度回転していることがある。pdf.js の `page.rotate` を尊重して描画する（Phase 1 では自動補正しない）
- **画像をデータ URI で送るサイズ**: 500KB の base64 は約 670KB。`runtime.sendMessage` の上限を避けるため、OCR リクエストは**ビューアページから直接送らず、background 経由**にする場合は文字列サイズに注意する（実装時はビューア → background に画像を渡さず、background が URL から取れないため、ビューア内 fetch も選択肢。CORS は localhost 許可済み）

## 7. 受け入れ基準

1. スキャン PDF（テキスト層なし・10ページ程度）をビューアで開くと、バナーで OCR 実行が示され、可視ページから順に訳文が表示される
2. OCR リクエストは既存の `baseUrl` に対する `model` 違いの1本だけで、追加プロセスを要求しない
3. 同じ PDF を開き直すと OCR は再実行されず、キャッシュから即座に訳文が出る
4. テキスト層のあるページとスキャンページが混在する PDF で、テキストページの翻訳結果が従来と完全に一致する
5. 位置付き出力（`paddle-spotting` / `dots-json`）のとき、訳文がおおよそ元の行位置に重なる
6. 位置なし出力でも対訳モードで原文と訳文が並び、読み取り誤りを目視できる
7. OCR 実行中にキャンセルでき、ビューアは停止しない
8. OCR モデル未設定時は「設定への導線」が出る（行き止まりにならない）
9. `baseUrl` が localhost 以外のとき、OCR は実行されず警告が出る
10. LLM サーバーを停止していても、テキスト PDF の表示・翻訳キャッシュ表示は従来どおり動く
11. `node tests/pdf-ocr-test.mjs` がパスする（bbox 正規化の往復、JSON 抽出、Markdown 正規化、キャッシュキー）
12. 基準モデル（PaddleOCR-VL 1.6）で §14 の評価セットを処理し、合格ラインを満たす

## 8. リスクと対策

| リスク | 影響 | 対策 |
| --- | --- | --- |
| モデル入れ替えによるスラッシング | 1ページ数十秒のオーバーヘッド | OCR パスを先に完了させる2段階実行。`--models-max 2` / `keep_alive` を設定画面で案内 |
| VRAM / RAM 不足（2モデル常駐） | ロード失敗・OOM | OCR モデルは 0.9B クラスを推奨。`pdfOcrMaxEdge` を下げる選択肢を提示 |
| コンテキスト超過で出力が切れる | OCR が途中で途切れる | `finish_reason: 'length'` を検出して失敗扱い。`-c` 拡大と `max_tokens` 調整を案内 |
| 幻覚（存在しない文字の生成） | 訳文に無い内容が混入 | 対訳モードで原文併置、`OCR` バッジ表示、低信頼ヒューリスティック（長さ比・記号比） |
| プロンプト/出力形式のモデル差 | パース失敗 | プロファイル選択 + `auto` 推定 + 失敗時 `generic` 再試行 |
| 位置情報の粗さ | オーバーレイがずれる | 位置なし/粗い場合は対訳列に逃がす。オーバーレイは補助と位置づける |
| vision 非対応モデルを選ぶ | 501 エラー | エラーを翻訳して表示。モデル一覧に vision 対応の印を付ける（Phase 2） |
| PaddleOCR-VL を llama.cpp で動かすと精度が落ちる（モデルカードの注記） | 誤認識の増加 | 受け入れ基準はこの構成で測り、不足なら PaddleOCR 公式パイプライン（vLLM / SGLang）と数値を比較する |
| `Spotting:` の位置トークンがサーバーで落ちる | 位置が取れない | 位置なしに降格して対訳表示。プロファイルを `paddle-ocr` にフォールバック |
| mmproj を読み忘れる | 501、または画像が無視される | §11 のサブフォルダ配置と `--mmproj` を手順として固定。設定画面に注意書きを出す |
| 回転したスキャン | 認識率低下 | `page.rotate` を尊重。自動補正は Phase 2 |
| 画像送信によるプライバシー懸念 | 外部送信の疑い | localhost 検証を必須化し、送信先をバナーに表示 |
| 大きな PDF でリクエストが多発 | サーバー負荷・待ち時間 | 500ページ超は既定で無効。可視ページ優先 + 中断 |

## 9. フェーズ計画

- **Phase 0 — スパイク（半日）**: PaddleOCR-VL 1.6 を立て、手元のスキャン PDF 1ページを canvas → base64 にして `curl` で投げ、`OCR:` と `Spotting:` の出力形式・位置の粒度・レイテンシを実測する。`Spotting:` が使えるかどうかで Phase 2 のオーバーレイ対応可否が決まる
- **Phase 1 — MVP**: FR-1、FR-2、FR-3（`generic` のみ）、FR-4（対訳のみ）、FR-5、FR-6、FR-7、FR-8。スキャン PDF が「読める」状態
- **Phase 2 — 位置付き・精度**: `paddle-spotting` / `dots-json` のパースと bbox 変換（オーバーレイ対応）、自動プロファイル推定、vision 対応マーク、回転補正、低信頼行の扱い
- **Phase 3 — 品質向上**: ページ分割（大きな図表のクロップ再認識）、表の扱い、長文ページの分割リクエスト
- **Phase 4 — 書き出し**: FR-9（不可視テキスト層付き PDF）

## 10. 未決定事項 (要確認)

1. **既定の有効/無効**: `pdfOcrEnabled` の既定を `false` にしたが、モデル選択時に自動で有効化してよいか
2. **画像の生成場所**: ビューアページで fetch するか、background に委譲するか（`runtime.sendMessage` のサイズと CORS の兼ね合い）
3. **OCR 対象の閾値**: 実質 20 文字未満でよいか。図のキャプションだけのページをどう扱うか
4. **対訳専用モードの見せ方**: 既存の「対訳」モードに OCR 原文を出すか、OCR 専用のレイアウトを新設するか
5. **`Spotting:` の粒度**: 行単位のポリゴンを段落にまとめる際、既存の `extractParagraphs` に渡す前にどこまで結合するか（Phase 0 の実測で決める）

## 11. 推奨サーバー構成（設定画面の補足として転記する想定）

### 11.1 最短で試す（スパイク用）

```bash
# llama.app（HF のモデルカード記載の手順）
llama serve -hf PaddlePaddle/PaddleOCR-VL-1.6-GGUF

# または Ollama
ollama run hf.co/PaddlePaddle/PaddleOCR-VL-1.6-GGUF
```

### 11.2 router mode で翻訳モデルと同居させる

```
D:/AI/gguf/
  plamo-3-translate-0.8b-Q8_0.gguf              # 翻訳（単体ファイルは直置き）
  PaddleOCR-VL-1.6/                              # vision モデルはサブフォルダ必須
      PaddleOCR-VL-1.6-GGUF.gguf                 # 936MB
      PaddleOCR-VL-1.6-GGUF-mmproj.gguf          # 882MB / ファイル名は mmproj で始める
```

```bash
llama-server --models-dir D:/AI/gguf --models-max 2 -c 8192
# 翻訳: {"model": "plamo-3-translate-0.8b-Q8_0.gguf", ...}
# OCR : {"model": "PaddleOCR-VL-1.6-GGUF.gguf", "messages":[{"role":"user","content":[
#         {"type":"text","text":"OCR:"},
#         {"type":"image_url","image_url":{"url":"data:image/jpeg;base64,..."}}]}]}
```

- `--models-max 2` で両方常駐（1 にすると入れ替えが発生して遅い）
- `-c` は 8192 以上。`Spotting:` は出力が長くなるため、位置付きで使う場合は 16384 を推奨
- 実装時はモデル名を固定値で埋めない。`/v1/models` の返す `id` をそのまま設定値に保存する（router mode はパス由来の ID を返すことがある）

## 12. 設計上の結論

- **OCR は「翻訳パイプラインの入口を差し替える」機能**として実装する。段落復元以降は変更しないため、キャッシュ・用語集・オーバーレイ・書き出しが自動的に効く
- **エンジンは同梱しない。** 既存のローカルサーバーに vision モデルを1つ足し、`model` フィールドで呼び分ける。manifest・CSP・権限・拡張サイズの変更はゼロ
- **位置情報は「あれば嬉しい」扱い**にする。取得できれば従来のオーバーレイ、できなければ対訳表示。どちらでも「読める」ことを受け入れ基準に置く
- **プライバシーは翻訳より厳しく**する。ページ画像はテキストより機微度が高いため、送信先を localhost に限定する検証を必須にする
- **テキスト層付き PDF の書き出しは Phase 4** に分離する。今回の目的は「読めるようにする」こと
- **基準モデルは PaddleOCR-VL 1.6 に固定**する。実装・受け入れテスト・設定画面の既定例はすべてこのモデル名で揃え、他モデルはプロファイル差し替えで対応する

## 13. 検討したが採用しなかったモデル

| モデル | サイズ | ライセンス | 不採用の理由 |
| --- | --- | --- | --- |
| GLM-OCR | 0.9B | MIT | Ollama で最も導入が楽だが、日本語が弱い（MDPBench 65.5 / 英語84.5、旧スキャン37.6）。位置付き出力も JSON スキーマ指定が必要 |
| dots.ocr | 3B | MIT | 多言語レイアウトは強いが 3B で重い。llama.cpp より vLLM 前提 |
| LightOnOCR-3 | 0.8B / 1B / 4B | Apache-2.0 | grounding の位置は優秀だが欧文中心で日本語が期待できない |
| Surya OCR 2 | 650M | 独自（寛容） | 日本語86.2%と軽量だが、配布が Python パッケージ中心で GGUF 経路が未確立 |
| OvisOCR2 | 0.8B | Apache-2.0 | ベンチ最上位（96.47）だが llama.cpp 経路が未確認 |
| HunyuanOCR 1.5 | 1.5B | Tencent独自 | llama.cpp 対応はあるが 1.5B で、汎用文書ベンチは低め（OmniParseBench 64.6） |

### 13.1 PLaMo 2.1-VL（PFN）について

**PFN は OCR 専用モデルを公開していない。** 画像を扱うのは `PLaMo 2.1-8B-VL` / `PLaMo 2.1-2B-VL`（2026年4月、GENIAC 第3期）だが、これは**エッジデバイス向けの VQA と Visual Grounding**（工場の作業分析・設備異常検出）を目的としたモデルで、文書 OCR の学習・評価（OmniDocBench 等）が存在しない。物体の位置は返せても、テキスト行の bbox は期待できない。

- サイズは 2B / 8B で、0.9B の専用モデルより重い
- HF の配布は Transformers 形式のウェイトが中心で、llama.cpp 用 GGUF の公式提供は確認できない
- ライセンスは PLaMo コミュニティライセンス（商用は登録＋売上条件）。個人利用なら問題ない

翻訳で PLaMo 3 Translate を使っており「同じベンダーで揃う」利点はあるため、**PFN が日本語ドキュメント OCR を目的としたモデルを出した時点で再評価する**（それまでは採用候補外）。

## 14. 評価セット（Phase 0 で使う）

ベンチマークの点数は英語・中国語の文書が中心で、日本語の古いスキャンでは大きく崩れる。モデル比較は次の5ページを自前で用意して行う。

| # | 種類 | 見たいこと |
| --- | --- | --- |
| 1 | 日本語の縦書き（官公庁の古いPDF） | 読み順が崩れないか |
| 2 | 和文の帳票・申請書（表とチェックボックス） | 表のセルが混ざらないか |
| 3 | 2段組の英語論文スキャン | 段の結合・読み順 |
| 4 | 傾き・ノイズのあるFAX | 耐性 |
| 5 | 図表のラベル入りページ | 図中テキストの扱い |

記録する指標と合格ライン:

- **文字の正しさ**: 本文の文字誤り率 5% 未満（目視で200文字程度を照合）
- **読み順**: 段落の順序破綻がないこと
- **位置の一致**: `Spotting:` 使用時、訳文の位置ずれが行の高さ以内に収まる行が 8 割以上
- **所要時間**: 1ページ 20 秒以内（GPU）／60 秒以内（CPU）

GLM-OCR を比較対象に残す場合は同じ5ページで測る（合計ダウンロードは約 2.4GB）。
